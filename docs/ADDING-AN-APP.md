# Adding an app

*Also available in [Brazilian Portuguese](pt-BR/ADICIONAR-UM-APP.md).*

> **For:** whoever wants to put a new app in the store, or fix one.
> **What is here:** the fit criteria, the folder, the manifest, the secrets, the store card, the checks and the pull request.
> **Where to go for the rest:** what each check proves in [TESTING.md](TESTING.md); every field in [REFERENCE.md](REFERENCE.md); the general rules in [CONTRIBUTING.md](../CONTRIBUTING.md).

This is the path from an idea to an app in the RoqueOS App Store. Each step names the check that holds it, so you know before the pull request what the CI will say.

## Before you start: is it a fit?

The store is curated. An app gets in when all of this is true:

- **It is alive upstream.** A release in the last twelve months, and the repository is not archived.
- **Its image is published by the project, or by a maintainer with a track record** (for example linuxserver.io), pinned to an exact tag or a digest.
- **It installs with one click.** If it needs an account, a token, a domain or hardware before its first start (a VPN provider, a Zigbee adapter, a federation domain), it is not one-click yet: open an issue instead, and see [the "Out of the store until it comes back" section of RETIRED.md](RETIRED.md#out-of-the-store-until-it-comes-back-17112026) for how those are handled.
- **The license lets anyone self-host it.** Source-available licenses (BSL, SSPL, Commons Clause) are allowed only when they permit self-hosting, and the store card says so.

Check [RETIRED.md](RETIRED.md) first: if the app left before, the reason is there.

## 1. The folder

```text
Apps/<AppName>/
├── docker-compose.yml   required
├── icon.png             required: square PNG, at least 192 px (we use 512)
└── README.md            required, generated in step 5
```

`<AppName>` is the app's own name in PascalCase, with no spaces. Screenshots and a thumbnail are optional: the store does not draw them today.

## 2. The manifest

Start from the shape below. It is an ordinary Docker Compose file with metadata under `x-casaos` (read by RoqueOS and by CasaOS clients) and RoqueOS extensions under `x-roqueos`.

```yaml
name: exampleapp
services:
  exampleapp:
    image: example/exampleapp:2.4.1          # exact tag or digest, never latest
    restart: unless-stopped
    ports:
      - target: 8080
        published: '8080'
        protocol: tcp
    volumes:
      - type: bind
        source: /DATA/AppData/$AppID/data    # $AppID is replaced by the installer
        target: /data
    environment:
      TZ: $TZ                                 # system variable
      SECRET_KEY: ${SECRET_KEY}               # generated, see step 3
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://localhost:8080/health']
      interval: 30s
      retries: 3
    x-casaos:
      ports:
        - container: '8080'
          description:
            en_us: Web interface
            pt_br: Interface web
      volumes:
        - container: /data
          description:
            en_us: Database and uploads, the folder to back up
            pt_br: Banco e uploads, a pasta para fazer backup
      envs:
        - container: SECRET_KEY
          description:
            en_us: "Session key: generated by RoqueOS at install, unique to this server"
            pt_br: "Chave da sessão: gerada pelo RoqueOS na instalação, única para este servidor"
x-casaos:
  architectures: [amd64, arm64]               # only what the image really publishes
  main: exampleapp
  category: Productivity
  author: RoqueOS Team
  developer: example                           # the upstream maintainer
  icon: https://cdn.jsdelivr.net/gh/roqueribeiro/roqueos-containers-list@main/Apps/ExampleApp/icon.png
  title:
    en_us: ExampleApp
  tagline:
    en_us: One line that says what it is for
    pt_br: Uma linha que diz para que serve
  description:
    en_us: What it does, for whom, and what makes it worth installing.
    pt_br: O que faz, para quem, e por que vale instalar.
  tips:
    before_install:
      en_us: The first account created is the admin.
      pt_br: A primeira conta criada é a de admin.
  port_map: '8080'
  scheme: http
x-roqueos:
  gerar:
    SECRET_KEY:
      formato: hex
      tamanho: 64
```

Rules that the checks enforce, with the premise that holds each one (the full table is in [TESTING.md](TESTING.md)):

- **Pinned image**, never `:latest` or a bare name (schema, P4).
- **`main`** names the service the store opens; with more than one service it is required (schema, P1).
- **`port_map`** is a host port published by `main` (schema).
- **`category`** is one of the store categories in [REFERENCE.md](REFERENCE.md) (P1).
- **`architectures`** lists only what the image publishes; declaring arm64 for an amd64-only image makes the app fail on a Raspberry Pi.
- **Every published port has a description** in `en_us` that says what it is for, and not a repetition of the field (P2). Give volumes and variables a description too, in both languages: the store card is built from them.
- **Folders live under `/DATA/AppData/$AppID/`.** P4 accepts any path under `/DATA/` and a short list of system mounts (such as `/var/run/docker.sock` or `/dev/dri`); any other host path needs `x-roqueos.motivo.volumeHost`.
- **`restart`** is present: `unless-stopped` for the app, `'no'` for a seed service that writes a first configuration and exits (P4).
- **`privileged`, `network_mode: host` or `cap_add`** only with a written reason in `x-roqueos.motivo` (P5).
- **An image that runs as a fixed user** cannot write a folder the installer creates as `root:root`: give it `PUID` and `PGID` when the image honors them, or a seed service that hands the folder to that user; a non-root `user:` does not help and P10 fails it (P10).
- **`tagline` and `description`** in `en_us` and `pt_br`, in Brazilian Portuguese (P7).

### An app with a database

Put the database, the cache and the app in the same manifest, and make the app wait for them:

```yaml
    depends_on:
      db:
        condition: service_healthy
```

The RoqueOS installer honors `service_healthy` and `service_completed_successfully`, so a seed service that copies a default configuration into an empty folder runs to completion before the app starts. [`Apps/Glance`](../Apps/Glance/docker-compose.yml) is a short example of a seed.

## 3. Secrets

Never write a password, a JWT secret, a session key or a database password in the manifest. Declare it and reference it:

| `formato` | Generates | Use for |
| --- | --- | --- |
| `hex` | `tamanho` hexadecimal digits | session and signing keys |
| `base64` | `tamanho` random bytes in base64 | keys that the app expects in base64 |
| `senha` | `tamanho` letters and digits | passwords |
| `uuid` | a UUID v4 | secrets that must look like a UUID |
| `laravel` | `base64:` plus 32 bytes | `APP_KEY` of Laravel apps |

The same variable used by two services (the database and the app, or inside a `DATABASE_URL`) is the same generated value. Add `mostrar: true` and a `descricao` to a login password the person needs: RoqueOS shows it once, right after installing. If the image ships with a login of its own that no variable can change, write it in `x-roqueos.senhaPadraoDaImagem` instead of leaving it only in a tip; the store card shows it in a highlighted line.

## 4. Text and icon

- `tagline` is one line; `description` is a short paragraph. Write the Brazilian Portuguese yourself, as a person in Brazil would say it: machine translation and European Portuguese are sent back.
- `icon.png` is a square PNG of at least 192 px that exists in the folder (P8). The `x-casaos.icon` URL points at it through the CDN.

## 5. The store card

```bash
yarn readme --app <AppName>
```

It writes `Apps/<AppName>/README.md` from the manifest: what it is, ports, folders, variables, first access, images and the official source. Do not edit it by hand: regenerate it whenever the manifest changes.

## 6. Run the checks

```bash
yarn validate
yarn revisao:app <AppName>
yarn test
```

`yarn revisao:app` prints each open premise with its reason. On Linux, also run `yarn boot <AppName>`; on any other system, the pull request runs it for you.

## 7. The pull request

Use a conventional commit title (`feat(catalog): add ExampleApp`). The template asks how you tested it and on which architecture. The CI runs the schema, the premises, the unit tests, the documentation check and the boot of every app the pull request touches. A maintainer from [CODEOWNERS](../.github/CODEOWNERS) reviews it, and once merged it reaches the store from `main`.
