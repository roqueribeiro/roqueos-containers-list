# Adicionar um app

*Tradução de [ADDING-AN-APP.md](../ADDING-AN-APP.md), a versão principal, em inglês. Se as duas divergirem, vale a em inglês.*

Este é o caminho de uma ideia até um app na App Store do RoqueOS. Cada passo diz qual checagem o segura, para você saber antes do pull request o que o CI vai dizer.

## Antes de começar: ele se encaixa?

A loja é curada. Um app entra quando tudo isto é verdade:

- **Ele está vivo no projeto original.** Uma release nos últimos doze meses, e o repositório não está arquivado.
- **A imagem é publicada pelo próprio projeto, ou por um mantenedor com histórico** (por exemplo a linuxserver.io), fixada numa tag exata ou num digest.
- **Ele instala com um clique.** Se ele precisa de uma conta, um token, um domínio ou um hardware antes de subir pela primeira vez (um provedor de VPN, um adaptador Zigbee, um domínio de federação), ele ainda não é de um clique: abra uma issue em vez disso, e veja a seção "Fora da loja até voltar" do [APOSENTADOS.md](APOSENTADOS.md#fora-da-loja-até-voltar-17112026) para saber como esses casos são tratados.
- **A licença deixa qualquer pessoa hospedar o app por conta própria.** Licenças source-available (BSL, SSPL, Commons Clause) só são aceitas quando permitem self-hosting, e a ficha da loja diz isso.

Olhe o [APOSENTADOS.md](APOSENTADOS.md) primeiro: se o app já saiu antes, o motivo está lá.

## 1. A pasta

```text
Apps/<AppName>/
├── docker-compose.yml   obrigatório
├── icon.png             obrigatório: PNG quadrado, no mínimo 192 px (usamos 512)
└── README.md            obrigatório, gerado no passo 5
```

`<AppName>` é o nome do próprio app em PascalCase, sem espaços. Screenshots e thumbnail são opcionais: a loja não desenha nenhum dos dois hoje.

## 2. O manifesto

Comece pelo formato abaixo. É um arquivo Docker Compose comum, com metadados em `x-casaos` (lidos pelo RoqueOS e pelos clientes CasaOS) e extensões do RoqueOS em `x-roqueos`.

```yaml
name: exampleapp
services:
  exampleapp:
    image: example/exampleapp:2.4.1          # tag exata ou digest, nunca latest
    restart: unless-stopped
    ports:
      - target: 8080
        published: '8080'
        protocol: tcp
    volumes:
      - type: bind
        source: /DATA/AppData/$AppID/data    # o instalador substitui $AppID
        target: /data
    environment:
      TZ: $TZ                                 # variável de sistema
      SECRET_KEY: ${SECRET_KEY}               # gerado, veja o passo 3
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://localhost:8080/health']
      interval: 30s
      retries: 3
    x-casaos:
      ports:
        - container: '8080'
          description:
            en_us: Web interface
            pt_br: Interface web
      volumes:
        - container: /data
          description:
            en_us: Database and uploads, the folder to back up
            pt_br: Banco e uploads, a pasta para fazer backup
      envs:
        - container: SECRET_KEY
          description:
            en_us: "Session key: generated by RoqueOS at install, unique to this server"
            pt_br: "Chave da sessão: gerada pelo RoqueOS na instalação, única para este servidor"
x-casaos:
  architectures: [amd64, arm64]               # só o que a imagem publica de verdade
  main: exampleapp
  category: Productivity
  author: RoqueOS Team
  developer: example                           # o mantenedor do projeto original
  icon: https://cdn.jsdelivr.net/gh/roqueribeiro/roqueos-containers-list@main/Apps/ExampleApp/icon.png
  title:
    en_us: ExampleApp
  tagline:
    en_us: One line that says what it is for
    pt_br: Uma linha que diz para que serve
  description:
    en_us: What it does, for whom, and what makes it worth installing.
    pt_br: O que faz, para quem, e por que vale instalar.
  tips:
    before_install:
      en_us: The first account created is the admin.
      pt_br: A primeira conta criada é a de admin.
  port_map: '8080'
  scheme: http
x-roqueos:
  gerar:
    SECRET_KEY:
      formato: hex
      tamanho: 64
```

As regras que as checagens cobram, com a premissa que segura cada uma (a tabela completa está no [CRITERIOS-DE-TESTE.md](CRITERIOS-DE-TESTE.md)):

- **Imagem fixada**, nunca `:latest` nem um nome sem tag (schema, P4).
- **`main`** dá o nome do serviço que a loja abre; com mais de um serviço, ele é obrigatório (schema, P1).
- **`port_map`** é uma porta do host publicada pelo `main` (schema).
- **`category`** é uma das categorias da loja listadas no [REFERENCIA.md](REFERENCIA.md) (P1).
- **`architectures`** lista só o que a imagem publica; declarar arm64 para uma imagem só amd64 faz o app falhar num Raspberry Pi.
- **Toda porta publicada tem uma descrição** em `en_us` que diz para que ela serve, e não uma repetição do campo (P2). Dê descrição também aos volumes e às variáveis, nos dois idiomas: a ficha da loja é montada a partir delas.
- **As pastas ficam em `/DATA/AppData/$AppID/`.** A P4 aceita qualquer caminho em `/DATA/` e uma lista curta de montagens do sistema (como `/var/run/docker.sock` ou `/dev/dri`); qualquer outro caminho do host precisa de `x-roqueos.motivo.volumeHost`.
- **`restart`** está presente: `unless-stopped` para o app, `'no'` para um serviço seed que escreve uma primeira configuração e sai (P4).
- **`privileged`, `network_mode: host` ou `cap_add`** só com um motivo escrito em `x-roqueos.motivo` (P5).
- **Uma imagem que roda como um usuário fixo** não consegue escrever numa pasta que o instalador cria como `root:root`: dê `PUID` e `PGID` quando a imagem respeita essas variáveis, ou um serviço seed que entrega a pasta para esse usuário; um `user:` não root não resolve e a P10 reprova (P10).
- **`tagline` e `description`** em `en_us` e `pt_br`, em português do Brasil (P7).

### Um app com banco de dados

Coloque o banco, o cache e o app no mesmo manifesto, e faça o app esperar por eles:

```yaml
    depends_on:
      db:
        condition: service_healthy
```

O instalador do RoqueOS respeita `service_healthy` e `service_completed_successfully`, então um serviço seed que copia uma configuração padrão para uma pasta vazia roda até o fim antes de o app subir. O [`Apps/Glance`](../../Apps/Glance/docker-compose.yml) é um exemplo curto de seed.

## 3. Segredos

Nunca escreva no manifesto uma senha, um segredo de JWT, uma chave de sessão ou a senha de um banco. Declare e referencie:

| `formato` | Gera | Use para |
| --- | --- | --- |
| `hex` | `tamanho` dígitos hexadecimais | chaves de sessão e de assinatura |
| `base64` | `tamanho` bytes aleatórios em base64 | chaves que o app espera em base64 |
| `senha` | `tamanho` letras e dígitos | senhas |
| `uuid` | um UUID v4 | segredos que precisam ter cara de UUID |
| `laravel` | `base64:` mais 32 bytes | `APP_KEY` de apps Laravel |

A mesma variável usada por dois serviços (o banco e o app, ou dentro de uma `DATABASE_URL`) é o mesmo valor gerado. Adicione `mostrar: true` e uma `descricao` a uma senha de login de que a pessoa precisa: o RoqueOS mostra o valor uma vez só, logo depois de instalar. Se a imagem vem com um login próprio que nenhuma variável consegue mudar, escreva isso em `x-roqueos.senhaPadraoDaImagem` em vez de deixar só numa dica; a ficha da loja mostra numa linha destacada.

## 4. Texto e ícone

- `tagline` é uma linha; `description` é um parágrafo curto. Escreva o português do Brasil você mesmo, como uma pessoa no Brasil falaria: tradução automática e português de Portugal voltam.
- `icon.png` é um PNG quadrado de no mínimo 192 px que existe na pasta (P8). A URL de `x-casaos.icon` aponta para ele pela CDN.

## 5. A ficha da loja

```bash
yarn readme --app <AppName>
```

Ele escreve o `Apps/<AppName>/README.md` a partir do manifesto: o que é, portas, pastas, variáveis, primeiro acesso, imagens e a fonte oficial. Não edite à mão: gere de novo sempre que o manifesto mudar.

## 6. Rode as checagens

```bash
yarn validate
yarn revisao:app <AppName>
yarn test
```

O `yarn revisao:app` imprime cada premissa aberta com o motivo. No Linux, rode também `yarn boot <AppName>`; em qualquer outro sistema, o pull request roda por você.

## 7. O pull request

Use um título de conventional commit (`feat(catalog): add ExampleApp`). O template pergunta como você testou e em qual arquitetura. O CI roda o schema, as premissas, os testes unitários, a checagem da documentação e o boot de todo app que o pull request mexe. Um mantenedor do [CODEOWNERS](../../.github/CODEOWNERS) revisa, e depois do merge o app chega à loja a partir da `main`.
